# Project Structure: Parallelizing Blockchain Computations

This document outlines the directory and file structure for the C++/MPI implementation of a sharded blockchain using PBFT.

---

## Core Directories

-   **`/src`**: Contains all C++ source code (`.cpp` files). This is where the core logic for the simulation, consensus, and blockchain mechanics resides.

-   **`/include`**: Contains all C++ header files (`.h` files). These files define the interfaces for the classes and functions implemented in `/src`.

-   **`/build`**: This directory is the destination for all compiled binaries and object files. It is created by the `Makefile` and is separated from the source code to keep the project clean.

-   **`/tests`**: Contains source files for unit and integration tests. These are crucial for verifying the correctness of individual components, such as the PBFT implementation and the sharding logic, before running large-scale simulations.

-   **`/results`**: Stores the output data from performance experiments. This includes raw timing data, CSV files, and graphs generated by the analysis scripts. This directory is essential for fulfilling the "Performance Measurement" section of the proposal.

-   **`/scripts`**: Holds helper scripts for automating tasks like running experiments, cleaning the build, and plotting results.

-   **`/docs`**: Contains supplementary project documentation.

-   **`/resources`**: Contains research papers and other reference materials used for the project.

---

## Key Files

### `Makefile`

-   **`Makefile`**: A placeholder for build automation. It will contain rules for compiling the C++ source code using `mpic++`, linking the necessary libraries, and placing the final executable in the `/build` directory.

### Source Code (`src/` and `include/`)

-   **`main.cpp`**: The main entry point for the simulation. This file will be responsible for initializing MPI, setting up the network topology (partitioning nodes into shards), generating transactions, and orchestrating the overall simulation flow as described in the proposal.

-   **`node.h` / `node.cpp`**: Defines a single node in the distributed network. Each MPI process will represent a `Node`. This class will manage a node's state, its role (e.g., leader, replica), and its communication with other nodes.

-   **`transaction.h` / `transaction.cpp`**: Defines the structure for a transaction. This will likely be a simple data structure that can be created, serialized, and passed between nodes.

-   **`shard.h` / `shard.cpp`**: Implements the logic for a shard (or "committee"). This includes managing the nodes within the shard's `MPI_Comm`, handling the transaction pool for the shard, and initiating the consensus process.

-   **`pbft.h` / `pbft.cpp`**: The core implementation of the Practical Byzantine Fault Tolerance (PBFT) consensus algorithm. This logic will be executed *within* each shard to allow its members to agree on a block of transactions in parallel. It will involve implementing the pre-prepare, prepare, and commit phases using MPI point-to-point and collective operations.

-   **`blockchain.h` / `blockchain.cpp`**: Manages the final, aggregated blockchain. The "final committee" will use this to assemble the blocks received from each shard into a single, ordered chain.

### Testing (`tests/`)

-   **`test_pbft.cpp`**: A test suite for the PBFT implementation. It will verify that the consensus algorithm works correctly under various conditions, including simulated faulty nodes.
-   **`test_sharding.cpp`**: A test suite for the sharding logic. It will verify that nodes are correctly partitioned into communicators and that transactions are distributed as expected.

### Scripts (`scripts/`)

-   **`run_experiment.sh`**: A shell script to automate the execution of the simulation on the `kraken` cluster. It will likely take parameters such as the number of nodes and the number of shards, run the MPI executable (`mpirun`), and save the output to the `/results` directory.
-   **`plot_results.py`**: A Python script (using a library like Matplotlib) to parse the data in `/results` and generate the performance graphs required by the proposal (Throughput vs. Shards, Latency vs. Shards, Speedup).

### Documentation (`docs/`)

-   **`PERFORMANCE.md`**: A document to formally present and analyze the performance results, including the graphs and tables outlined in the project proposal.
